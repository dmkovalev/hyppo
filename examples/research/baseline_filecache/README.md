# Базовая линия: корректно настроенный файловый кэш

Спецификация: `docs/superpowers/specs/2026-09-23-baseline-filecache-design.md`.

Конвейер Brugge (154 задачи: 2 `p1` + 8 `hyb` + 16 `wct` + 128 `opr`) читает из общего SQLite-хранилища 4 сущности
(gains, tau, well_status, corey_ref); 6 пар «сущность → правило». Объявленная пара —
живая версия сущности в `params` правила; необъявленная — постоянная `v1`.
Для p ∈ {0; 0,25; 0,5; 0,75; 1} (17 подмножеств) и 5 правок (4 сущности + контроль
`ridge`) сравниваются множество пересчёта Snakemake (`snakemake -n`,
`--rerun-triggers mtime params`) и план комплекса (алгоритм 1 + алгоритм 4) с
эталоном S — задачами, чей выход изменился при полном пересчёте после правки.
«Неверные» результаты вычисляются аналитически: задача из S неверна, если не
пересчитана или прочла неверный файл-родитель.

Запуск: `bash examples/research/baseline_filecache/run_all.sh small` (дымовой),
`... run_all.sh full`. Результаты: `results/results_{grid}.json`,
`results/missed_vs_p_{grid}.pdf`. Требуется `F:/git-repos/diss/.venv-cache` (Snakemake)
и данные `thesis/papers/brugge_run` (или `HYPPO_BRUGGE_RUN`).

Время: `t_plan` — только алгоритм 4 (граф строится один раз, `lattice_build_s`);
`t_snakemake_dry` — полный вызов `snakemake -n`, включая запуск процесса и проверку
триггеров, то есть реальную цену планирования инструментом.

Интерпретация: переменная сущности входит в уравнение модели потребителя, которое
пишется в любом случае; отдельной записи о зависимости для каждого потребителя в
конвейере комплекс не требует (`declarations_hyppo = 0`).

## Оговорки интерпретации

- Пар «сущность → потребитель» 6, а не 7, как в первоначальной спецификации:
  `fit_opr` не читает `gains` напрямую. Уровни p = 0; 0,25; 0,5; 0,75; 1 дают
  0, 2, 3, 5, 6 объявленных пар.
- `t_plan` — это только вызов алгоритма 4 внутри процесса, без построения графа
  (построение вынесено в отдельную метрику `lattice_build_s`, выполняется один раз).
  `snakemake -n`, в свою очередь, включает запуск интерпретатора, разбор Snakefile и
  построение DAG. Прямое сравнение `t_plan` и `t_snakemake_dry` показывает порядок
  накладных расходов конкретного инструмента, а не скорость одной и той же операции
  на одинаковой входной структуре.
- `declarations_hyppo = 0` — по построению, а не по результату измерения: переменная
  сущности входит в уравнение модели-потребителя, которое пишется в любом случае;
  отдельной записи о зависимости, которую можно забыть или скрыть, в конвейере нет.
- Триггер `params` в Snakemake сравнивает *множество значений* параметров одной
  ревизии к другой. В каждом испытании выполняется одна правка одной сущности —
  скрытой маскировки изменений внутри одного и того же значения параметра нет.
- Эталон S предполагает, что `crm_fit` не перезапускается после внешней правки
  `gains`/`tau`: правка сделана внешним инструментом (например, ручной корректировкой
  промысловой ГТМ), по отношению к `crm_fit` она внешняя, а не следствие его логики.
  В комплексе такой правке соответствует отдельная гипотеза-хранилище ниже `crm_fit`
  по каскаду, а не пересчёт самого `crm_fit`.
- 154 задачи вместо 156 контрольного опыта `filecache_control`: здесь нет служебных
  правил `aggregate` и `all`; числа 136/156 из диссертации к этому прогону не относятся.
- Лишних пересчётов (`snakemake_extra`, `hyppo_extra`) нет ни в одном из 85 испытаний;
  при p = 1 E = P_ne = S, то есть число запусков у Snakemake и комплекса одинаково.
  Выигрыш комплекса в этом эксперименте — только в отсутствии пропусков при неполных
  объявлениях, а не в числе запусков.
- Сравнение выходов между базовым прогоном и эталоном идёт по дайджесту SHA-256 с
  округлением значений до 1e-9. На другой машине (иной BLAS/LAPACK, иной порядок
  операций) возможны ложные различия дайджестов при численно тождественном
  результате. Эталонные числа в этом README следует считать полученными на одной
  машине; для воспроизведения — пересчитывать `truth_sizes` заново, а не сравнивать
  побайтно со значениями отсюда.
- На small-сетке (2×1×1×1 = 7 задач) доли пропущенных — грубые (шаг 1/4 на
  4 задачах-потребителях), результат подходит для дымовой проверки конвейера, но не
  для содержательных выводов. Содержательные выводы — по full-сетке (154 задачи).

## Результаты (full)

Полная сетка: 154 задачи (2 `p1` + 8 `hyb` + 16 `wct` + 128 `opr`), 5 эталонов, 85 испытаний
(17 подмножеств объявлений × 5 правок). `truth_sizes` (размер эталона S — число задач,
чей выход изменился при полном пересчёте после правки):

| gains | tau | well_status | corey_ref | ridge |
|---|---|---|---|---|
| 136 | 136 | 136 | 144 | 136 |

Совпадает с ожиданием (gains 136, tau 136, well_status 136, corey_ref 144, ridge 136).

`lattice_build_s` = 7.90 с (алгоритм 1, один раз на сетку); `t_plan_median_s` = 0,00081 с
(алгоритм 4, медиана по 85 испытаниям); `t_snakemake_dry_median_s` = 1,05 с
(`snakemake -n`, включает запуск процесса и разбор Snakefile — см. «Оговорки
интерпретации»).

Сводка по p (среднее/мин/макс по 4 содержательным правкам — `ridge` исключён как
контроль; для p=0 и p=1 подмножество единственно, поэтому mean=min=max):

| p | declarations | snakemake_missed_share [min–max] | snakemake_wrong_mean | snakemake_executed_mean | hyppo_missed_max | hyppo_planned_mean | S_mean |
|---|---|---|---|---|---|---|---|
| 0.00 | 0 | 1.000 [1.000–1.000] | 138.0 | 0.0 | 0 | 138 | 138 |
| 0.25 | 2 | 0.514 [0.000–1.000] | 90.0 | 67.2 | 0 | 138 | 138 |
| 0.50 | 3 | 0.356 [0.000–1.000] | 62.0 | 88.8 | 0 | 138 | 138 |
| 0.75 | 5 | 0.106 [0.000–1.000] | 20.8 | 123.6 | 0 | 138 | 138 |
| 1.00 | 6 | 0.000 [0.000–0.000] | 0.0 | 138.0 | 0 | 138 | 138 |

Критерии успеха спецификации выполнены на full-сетке: при p=1 доля пропусков
Snakemake равна нулю (равенство E=S во всех 4 содержательных испытаниях и в контроле
`ridge`); доля пропусков растёт монотонно при уменьшении p (0 → 0,106 → 0,356 →
0,514 → 1,000); у комплекса пропусков нет ни при одном p (`hyppo_missed_max = 0`
везде). Разброс min–max в 1,000 при p=0,25/0,5/0,75 — ожидаемое следствие того, что
среди 5 случайных подмножеств одного уровня попадаются как подмножества, полностью
покрывающие правку одной конкретной сущности (missed=0 для неё), так и полностью её
не покрывающие (missed=1 для неё); при усреднении по 4 сущностям получается
промежуточная доля. Самопроверки (`self_checks`) прошли без ошибок, включая контроль
`ridge` (E=P=S при любом p) и точное равенство E=S при p=1 для каждой из 4
содержательных правок.
